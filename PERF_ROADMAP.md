# zipp-vm Performance Parity Roadmap

> Engine: `crates/zipp-vm/src` (register VM, NaN-boxed Values, per-call-site inline caches, dynasm x64 JIT tiers, whole-heap mark-sweep GC). Target: close the gap to V8/node on the real-world benches in `bench/real/*.js`.

## 1. Framing — what "parity" means and the honest bottom line

"Parity" here is measured as the **`zipp-jit / node` wall-time ratio** on `bench/real/*.js` (lower is closer; `1.0x` = parity). The engine today runs its hottest code as *"interpreter ops, inlined into native, but still NaN-boxed and tag-guarded on every operation"* — fast relative to a tree-walker, but carrying a per-op boxing/guarding tax that V8's optimizing tier does not pay, on top of a non-moving whole-heap GC whose raw allocation is ~214 ns/object vs node's ~10 ns.

**The honest bottom line, stated up front so no stage over-promises:**

- **Contained fast-paths (Stage 0) close roughly half the remaining gap on the alloc/builtin-bound benches** by deleting redundant work (per-value `toJSON` probes, O(n) dictionary deletes, hole-`in` prototype walks, regex result allocs). They move json/polymorphic/sparse/regex out of the 5–13x range toward a **~3–4x band** without any substrate change.
- **Getting into a ~2–3x band broadly** requires the codegen substrate work in **Stage 1** (widen the unboxed regalloc path to bitwise/int/TA kinds; inline non-leaf and closure-capturing callees).
- **Sub-2x across the board requires the substrate rewrites**: a generational **nursery GC (Stage 2)**, **shared hidden classes + megamorphic stub cache (Stage 3)**, and an **optimizing/speculative JIT tier with real SSA IR + deopt (Stage 4)**. These are weeks-to-months each and carry real correctness risk (a moving collector over a tagged-index heap; speculative deopt soundness).
- **True parity (~1.0–1.2x) is only reachable on `typedarray`** (unboxed numeric kernels — axpy/dot already measured 1.3–1.6x) and **`map-set` (~1.4x, already the closest)**. Everything else has a structural floor: `parse ~1.8x`, `json ~2x`, `markdown ~2x`, `class ~2x`, `polymorphic ~2–2.5x`, `async ~1.5x`, `regex ~5x without a native-code (Irregexp-class) regex JIT`, and `sparse` needs a dedicated sparse-dict rewrite beyond the packed-holey fast path.

This document is the durable, checkable plan. Each task carries its own file anchors, dependencies, validation + gate, expected gain, effort, and risk. Check tasks off as they land.

## STAGE 0 — Contained fast-paths

**Stage summary.** Effort: days (S/M tasks only). Risk: low–med (no new tier/GC/object-model; all changes are local fast-paths behind existing semantics, each independently gateable). Aggregate expected effect vs the **live** baseline: json 5.82x→~3.5x, polymorphic 4.74x→~3x, sparse 8.40x→~4x, regex 12.67x→~8x, plus incidental json/parse help from shared dedup. **Confirmed root cause for T0.2:** the polymorphic dictionary objects (60 props) cross `PROP_INDEX_THRESHOLD=12`, so the index is active, and each of the ~900k deletes (`delete obj["prop_"+p]`, half of 60 per object × 30000 objects) triggers the O(n) `remove_slot` rescan (`heap.rs:156-160`) PLUS three O(n) `Vec::remove` shifts (`heap.rs:365-367`). With ~30 deletes per object on a ~60-slot map, that is the dominant cost.

## STAGE 1 — Widen unboxed regalloc + leaf/closure inlining

**Summary.** Effort: weeks. Risk: med–high (heavy codegen, all on a branch behind an opt-in flag, default flipped last). Aggregate expected effect: typedarray 3.25x→~1.5–2x, parse 3.4x→~2.3x, markdown 4.6x→~2.8x, plus incidental wins on json/class/polymorphic loops with `|0`/`&` idioms. No new substrate — every task reuses the existing INT (i64-home), REGALLOC (f64-home), leaf-inline, and Tier-C emitters.

**Path facts (verified):** dispatch order in `compile_region` (`codegen.rs:888-963`) is SROA → INT → REGALLOC → MEM. **Cross-cutting soundness obligations (every task):**
- Any new admission must keep the bail/flush contract: a guard miss flushes all homes (or records the resume ip pre-effect) and resumes the interpreter at a *re-runnable* ip. Side-effect-freedom-before-deopt (`seen_effect`, `codegen.rs:2629`) must hold for any op that can bail after a global/heap write.
- INT path: every i64-home result that can leave `[-2^53,2^53]` needs `emit_i53_guard`; bitwise results are exact i32 (or u32-as-double for `>>>`) so guard-free, but must be re-canonicalised when consumed by following arithmetic (T1.2).
- New TA kinds: the per-access identity+kind guard already exists (`jit_ta_snapshot` writes {0,0,0} on a kind/identity mismatch → guard miss → helper); adding a kind only widens `plan_region`'s admission, the runtime guard stays the backstop.
- Develop on branch `stage1-unboxed-inline` behind `ZIPP_JIT_STAGE1`; flip default in T1.9 only after the full gate passes.

## STAGE 2 — Generational nursery GC (moving young-gen collector)

**Effort: weeks→months. Risk: HIGH** (moving collector over a NaN-boxed tagged-INDEX heap that today depends on indices never changing). **Aggregate expected effect:** alloc ~214ns → ~30–50ns; GC-time fraction (15–33% measured) → single digits on alloc-bound benches. Direct moves: async 3.8x→~2–2.5x (THE case: 7.7M short-lived promises), json 4.5x→~3.5x, parse 3.4x→~3x, sparse/markdown indirectly. typedarray/map-set largely unaffected.

The whole edifice today rests on `gc.rs:1-7`: *"`Value` references objects by INDEX … NON-MOVING … every existing index stays valid. That sidesteps having to rewrite indices in the side tables, the register file, and the JIT."* This stage deliberately reintroduces exactly that index-rewriting, scoped to a young generation. **The moving collector ships LAST, behind `ZIPP_NURSERY` opt-in, default-off until T2.11.**

**Measured facts this plan is built on (verified):**
- `heap.rs:1524-1545` `Heap { objs: Vec<HeapObj>, versions: Vec<u32>, free: Vec<u32>, live, gc_requested, gc_threshold }`. Single flat Vec; `Value::heap(idx)` packs the `objs` index (`value.rs:107-109`, 48-bit payload, `heap_index()` `value.rs:198-200`).
- `heap.rs:1576-1592` `alloc`: pop free-list slot (bump `versions[]`) or push. `heap.rs:1623-1627` `free_slot`: tombstone to `Date(NaN)`, bump version, push to free. The ONLY alloc path.
- `gc.rs:65-452` `gc()`: mark-sweep; roots `gc.rs:113-377`, `trace_edges` `gc.rs:455-636`, sweep+prune `gc.rs:385-447` (38 `retain` calls pruning index-keyed side tables).
- `dispatch.rs:142-146` — `maybe_gc()` at the TOP of `dispatch_body` (frame-transition safe point). `dispatch.rs:2573` — second safe point. `gc.rs:56-63` `maybe_gc` gates on `gc_lock == 0 && gc_floor != 0 && (requested || stress)`.
- **JIT-GC interaction (decisive):** native code is entered only at `ip == 0` (`dispatch.rs:176`), never re-enters mid-function. BUT region/Tier-C helpers (`jit_call_ic`, `jit_call_method_ic`, `jit_get_prop_slow`, `jit_concat`, …, `dispatch.rs:5775-5808`) re-enter the interpreter → can hit `maybe_gc`. So **a GC can fire with a native frame live on the C stack**, holding raw obj_bits (IC table `codegen.rs:565-571` `IcEntry.obj_bits: u64`) and raw register/global Values (pinned `rbx`/`r12`).
- **Register file is capacity-pinned** (`engine.rs:2400-2414`, `reg_capacity`): reserved to worst-case at startup, never reallocates → **can be fixed up in place after a move.** `globals` similarly fixed.
- `value.rs:37-59` tag layout: Heap = `0x7FFD`, payload = low 48 bits. **No spare tag/payload bit** for a forwarding flag — forwarding must live in the HeapObj/header, not the Value.
- Transient unrooted index sets a mid-`construct` move would corrupt: `super_called` (`mod.rs:459`), `this_tdz` (`mod.rs:465`), `super_this` KEYS (`mod.rs:472`).

## STAGE 4 — Optimizing / speculative JIT tier (Tier D)

**One-line summary:** Effort = weeks-to-months (XL); Risk = hi (heavy codegen, deopt-soundness critical); **aggregate effect** = the umbrella that turns "boxed+guarded inlined interpreter ops" into unboxed, type-specialized, inlined, whole-function native code — moves parse/json/markdown/class/polymorphic/async from ~3–4.5x toward floors (~1.8–2.5x) and lets typedarray reach ~1.0–1.2x. No single task gets a bench to parity; the SSA substrate (T4.1–T4.4) is the shared chokepoint every later win depends on. Develop the whole tier behind `ZIPP_TIER_D` (default-OFF) on a branch; flip default only after the full gate is green for several consecutive milestones.

**Why a new tier:** today's emitters lower straight from bytecode per-op (`compile_region`, `compile_proto_mem` walk `proto.code[s..=e]` and `match instr`), so every cross-op optimization (range analysis, escape analysis, global regalloc) is re-derived ad hoc (`analyze_int_guards`, `plan_field_promotion`, `XmmAlloc` are separate bytecode walks). Tier D introduces a real SSA IR between bytecode and codegen so those analyses compose. The existing region paths stay as Tier B; Tier D is a *new* whole-function compiler selected by tiering policy (T4.13), declining to Tier B/C/interpreter on any unsupported construct.

**Architectural facts (verified):**
1. Codegen emits straight from bytecode per-op — no SSA IR exists.
2. Type feedback exists but scattered: interpreter ICs (`site_ics`, `IcEntry`), `mi_recv` recorded receiver sets, read at compile time by `build_method_inline_plan`/`build_leaf_inline_plan`/`build_ta_pin_plan` (engine.rs).
3. Deopt/resume is uniquely simple: region bail (`emit_region_bail`) writes resume-ip to `[rsi]`; the interpreter resumes on the *shared* register window (`self.regs[base..]`). No frame reconstruction today because unboxed homes are flushed at every exit (`emit_region_restore`, RegionPlan `num_regs`/`bool_regs`/`globs`).
4. Unboxed homes-guarded-once-at-entry already works in `compile_region_regalloc` (RegionPlan: `live_in_regs`+guard, `reg_home: Home::Xmm/Gpr`) — but only per-loop, numeric-only, declining Bitwise (codegen.rs:1225) and rebox-per-op on MEM (`load_num_xmm`/`store_xmm`).
5. SROA = narrow escape analysis (`plan_field_promotion`, single non-escaping global object).
6. Guard substrate = `heap.version_of`/`bump_version` + identity bits; deopt eviction = `note_region_resume`/`OSR_DEOPT_LIMIT`.

**Cross-cutting soundness obligations (every task inherits):**
1. **Deopt live-map completeness (T4.4):** any value in a register/spill-slot MUST appear in the safepoint live-map with its box-form, or a deopt corrupts the frame. The analogue of the GC "complete root set" invariant — verify with `ZIPP_TIER_D_DEOPT_EVERY` torture.
2. **Speculation guards mirror existing guards:** identity = Value bits, shape = `heap.version_of`/`bump_version` (heap.rs:1656/1670), exactly what ic.rs and `FieldSyncPlan`/`IcEntry` check — do NOT invent a new guard discipline.
3. **Effect-after-deopt ordering:** a deopt resumes the interpreter at the op's `ip` and RE-RUNS it (the `emit_region_bail` model). A speculated op that already committed a side effect before its deopt point would double-apply — preserve `callee_leaf_ok`'s rule (codegen.rs:2602, "NO deopt-capable op after any effect") generalized: place all deopt-capable guards BEFORE the first observable effect in each block, or split the safepoint.
4. **GC interaction (T4.9):** scalar replacement removes allocations the GC root-set assumed; the deopt materializer re-allocates at a safe point (`gc_lock`/`maybe_gc` gc.rs:49/56) — gate with `ZIPP_GC_STRESS`.

### Part B — Pointer compression (LOW PRIORITY; mostly already done)

**Honest assessment: V8-style pointer compression does not apply here.** V8 compresses 64-bit heap *pointers* to 32-bit offsets-from-a-base to halve object field size. Object-to-object references are 32-bit indices inside 8-byte Values. There is no 64-bit raw pointer to compress. So B reduces to two small optional footprint tasks — not an epic.

## 6. Recommended execution order

The stages are not strictly sequential; they interleave. Recommended order with rationale:

1. **Stage 0 first — the down-payment.** Days of work, low risk, closes ~half the gap on json/polymorphic/sparse/regex with no substrate change. Every task is independently gateable and correctness-preserving. Ship these incrementally; they buy time and prove the measurement protocol before the expensive substrate work. *(Note T0.2's tombstone delete is the highest-risk Stage-0 item — give it its own verifying build day and GC-stress run.)*

2. **Stage 1 next — widen the existing JIT substrate.** Weeks, med-hi risk, but it reuses the existing INT/REGALLOC/leaf-inline emitters (no new tier, no GC change). It is the cheapest path into the ~2–3x band on typedarray/parse/markdown and is the natural precursor to Stage 4 (Stage 4's T4.7/T4.8 *subsume* Stage 1's bitwise-admission and inlining via real SSA — so Stage 1 is both an immediate win and a learning/de-risking pass for the Tier-D versions). All behind `ZIPP_JIT_STAGE1`, flip default last.

3. **Stage 5 Part A (regex) runs in parallel, independently.** It touches only `crates/regress-patched` + the thin `proxy_regexp.rs` glue, shares no code with the VM core, and its first landing (TA.7, flag OFF) is a guaranteed no-op. A separate developer/track can carry it concurrent with Stages 0/1. Part B (pointer compression) is ~zero work — do TB.1/TB.2 opportunistically.

4. **Substrate rewrites: Stages 2 and 3 BEFORE Stage 4.** Sub-2x broadly needs the object model (Stage 3 shared hidden classes) and the allocator (Stage 2 nursery). Both are independent of each other and of Stage 1, and each is independently gateable behind its flag (`ZIPP_NURSERY`, `--features shapes`).
   - **Stage 3 (hidden classes) should generally precede Stage 4**, because Stage 4's speculative tier (T4.3 feedback, T4.6 shape-keyed specialization) reads shape-based type feedback — the consolidated shape model (T3.18) is what lets Tier D speculate cleanly. Stage 4's brief explicitly notes "unblocks Stage 4's optimizing tier consuming shape feedback."
   - **Stage 2 (nursery) can land before, during, or after Stage 3** — it is orthogonal to the object model. Prioritize it when the alloc/GC fraction (measured by T2.0) is confirmed to dominate the target benches (async especially). Stage 2 is the single highest-risk stage (a moving collector over a tagged-index heap); its measure-first task T2.0 is a hard gate — if infant-mortality is low on the target benches, do not build the nursery.

5. **Stage 4 last — the optimizing tier (Tier D).** It is the umbrella that consumes everything: it generalizes Stage 1's inlining and bitwise admission into real SSA, reads Stage 3's shape feedback, and (via T4.9 scalar replacement) reduces the allocation load Stage 2 collects. Build its SSA substrate (T4.1–T4.4, the deopt keystone) only after the cheaper wins are banked and the object/alloc model is stable, so the speculation has a stable foundation to guard against.

**Summary interleave:** `Stage 0` → `Stage 1` (‖ `Stage 5A`) → `Stage 3` ‖ `Stage 2` → `Stage 4`. Regex (5A) and pointer-compression (5B) float independently throughout.

**Where each stage lands you (cumulative, honest):** Stage 0 = ~3–4x band on the worst benches. ## 7. How to use this doc

- This is the durable, checkable perf roadmap. **Check off tasks (`- [ ]` → `- [x]`) as they land**; mark in-progress with 🔜.
- **Every task carries its own gate** (the STANDING GATE in §2, plus any task-specific additions like `ZIPP_GC_STRESS` or a deopt-torture run). Do not mark a task done until its `Validate:` line passes in full, BOTH `--jit` and `--nojit`, REG=0 vs the 48466 test262 baseline.
- **Develop heavy codegen / GC / object-model changes on a branch behind the named opt-in flag** (`ZIPP_JIT_STAGE1`, `ZIPP_NURSERY`, `--features shapes`, `ZIPP_TIER_D`, `ZIPP_REGEX_DFA`) and **flip the default in the stage's final "land" task only**, after the full gate is green across multiple milestones.
- **Gains marked `measured` are confirmed; `inferred` are projections** from the gap analysis. Re-measure with `bash bench/run_real.sh` and update the per-bench target table (§4) as real numbers come in. Record landed ratios in MEMORY (`real-bench-perf-campaign.md`).
- **Respect the floors (§4).** Several benches have structural floors no amount of contained work will beat (regex ~5x without TA.14; sparse needs a sparse-dict rewrite; json/markdown/class/parse/polymorphic ~1.8–2.5x). Only typedarray (~1.0–1.2x) and map-set (~1.4x, already there) are true-parity candidates — do not burn effort chasing 1.0x elsewhere.
