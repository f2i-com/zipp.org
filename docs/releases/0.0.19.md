# ZIPP 0.0.19

A review of the whole project found 324 verified defects; this release fixes all
of them, and gives the browser GPU path the operations a neural network needs.

## Downloads

- `zipp-wasm-0.0.19-web.zip`: JavaScript-only browser engine, TypeScript bindings and Worker host SDK.
- `zipp-wasm-0.0.19-web-python.zip`: JavaScript + Python, with the browser GPU adapter, CPU WASM kernels and Torch compatibility guide.
- Native x86-64 CLI archives for Windows and Linux: JavaScript + experimental Python. A source build with `--no-default-features` produces a JavaScript-only CLI.

Every WASM archive includes `BUILD-INFO.txt`, `PROFILE.json` and `SHA256SUMS`.
Publishing requires CI and the full security workflow at the exact tagged commit.

## Correctness

- Native built-ins no longer hand back collected objects. `Object.entries`,
  `Object.assign`, object spread, `flat`, `apply`, the descriptor readers and
  about twenty more gathered results into host memory and then ran guest code —
  a getter, a Proxy trap, a species constructor — which could collect what the
  walk had already produced. Sixteen of twenty-seven probes failed every round
  under GC stress; none do now, across seven mode combinations.
- The JIT tiers answer what the interpreter answers. Nine programs changed
  their result as they warmed up: a zero product losing its sign, a hoisted
  `length` racing the accessor it was meant to precede, a recycled register
  making a warm call site invoke the previous callee, a frozen array still
  writable through a compiled store, and a private method reachable from a
  class that never declared it.
- `Number.prototype.toString(radix)` keeps the fraction and the sign, so
  `Math.random().toString(36).slice(2)` no longer returns the empty string.
- Lone surrogates survive the string built-ins, so `s.split('').join('')` no
  longer corrupts text containing an emoji.
- A non-ASCII character can no longer end the process: the Temporal ISO parsers
  advance by ASCII digit pairs rather than slicing UTF-8 at a byte offset.
- A frozen array's elements are not writable through `Object.assign`, a Proxy
  or a prototype, and `Reflect.set` reports what it actually did.
- Four builders that could abort the host process — `split`, `normalize`,
  `toLocaleUpperCase` and `concat` — are charged against the string cap first
  and raise RangeError.
- Intl formatting: currencyDisplay, exact BigInt digits, numeric collation,
  English ordinal plurals, percentage rounding, `longOffset`, sub-minute zone
  offsets, and the doubled month suffix in Japanese and Chinese.
- `sys.exit(3)` from a Python program exits 3, and an argparse usage error
  exits 2.

Test262: 102,373 of 102,656 executions pass, with no regression against the
previous release and four tests newly passing.

## Machine learning in the browser

The graph protocol carries version 2 on every backend — the JavaScript
reference, the WebAssembly kernels, WebGL2 and WebGPU:

- rank up to four with NumPy right-aligned broadcasting;
- neg, exp, log, sqrt, tanh, sigmoid, relu and an exact-erf gelu;
- permute and reshape, axis and whole-tensor reductions with keepdim;
- numerically stable softmax and log_softmax, and batched matmul;
- a fused cross-entropy against integer class targets with its gradient;
- SGD, momentum and Adam update steps, so optimizer state stays on the device.

`torch.compile(training=True)` records all of it from ordinary Torch code:
relu, gelu, sigmoid or tanh layers, softmax and log_softmax, MSE-style losses
or `F.cross_entropy` against integer class targets, trained with SGD (momentum,
dampening, Nesterov, weight decay), Adam or AdamW — with momentum buffers and
Adam moments read from `optimizer.state`, updated in the graph and written back
with the weights. Ten model/loss/optimizer combinations track PyTorch 2.11 step
for step to float32 rounding (losses within 2.4e-7, weights and optimizer state
within 1.2e-7 over four steps).

A compiled step can also be prepared once and kept on the device:
`compiled.prepare(x, target)` records the step from an example call and returns
a session whose `step(callback, x, target)` and `steps(callback, batches)` feed
only each step's batch — weights, momentum buffers and Adam moments carry from
step to step on the device (a `zipp_gpu.Graph.prepare` session underneath), the
Adam step count advances per executed step, `sync(callback)` copies weights,
optimizer state and the last gradients back into the model and
`optimizer.state`, and `dispose()` frees the device tensors. While a session is
live, compiled calls and eager `optimizer.step()` on its parameters are refused.
Six model/loss/optimizer combinations over six distinct batches track PyTorch
2.11 after `sync()` to the same rounding (losses within 2.4e-7, state within
1.2e-7), eager steps continue the trajectory afterwards, and without a host the
session equals the same steps as separate compiled calls bit for bit. The
protocol's 64 outputs bound a prepared Adam step to 15 parameter tensors;
beyond that `prepare()` raises rather than falling back. Driving the engine from
Python in Chrome on an RTX 5090, the 784-256-10 batch-64 Adam step costs 74 ms
per `compiled()` call on WebGPU (most of it the guest's own recording and the
2.4 MB commit), 5.1 ms per `prepared.step`, and 1.8 ms per step with eight steps
per `prepared.steps` run (WebGL2 89 / 3.3 / 2.2 ms, WebAssembly 74 / 4.9 / 3.6 ms).

WebGPU submits one command encoder per execute over a buffer pool, WebGL2
renders to R32F where the device offers it, both key pipelines by operation
rather than by shape, and the WebAssembly kernels are rebuilt with SIMD and a
tiled matmul. Limits derive from the device and are only lowered by the host, so
a 784-256-10 network at batch 64 is accepted where fixed ceilings refused it.

On an RTX 5090 in Chrome, one Adam step of that network: WebGPU 7.8 ms warm,
WebGL2 5.6 ms, WebAssembly 3.9 ms, JavaScript 27.0 ms — same loss sequence on
all four, worst deviation from the reference four ulp of the GPU's own `exp`.

Prepared sessions remove what that step spent outside the GPU.
`runtime.prepare(program, {resident})` validates and plans once; `input` nodes
without data are fed per step and may carry an output, so weights, momentum
buffers and Adam moments never leave the device; `session.run(steps)` executes
one or many steps in a single submission with only the named outputs read back.
At the runtime level the same step is 7.5 ms per `execute()` with everything
read back, 3.6 ms per single-step run and 0.79 ms per step at eight steps per
run on WebGPU (WebGL2 0.81 ms, WebAssembly 1.64 ms); five session steps equal
five chained executes bit for bit on all four backends. What remains per
submission is Chrome's own ~2.6 ms wait for GPU work, which a multi-step run
amortises. Sessions are bounded per tenant (count, steps per run, resident
bytes) and named by random ids a guest cannot forge. A run that fails after
device work began - a backend error, a non-finite readback, a failed map -
leaves carries and residents at no step in particular, so it poisons the
session: `run` and `download` refuse with `STATE`, the error reply says
`poisoned: true`, and only `dispose()` remains; a run refused by validation
leaves the session as it was. The Python `Session` follows the same rule,
hosted or on the reference.

The JavaScript reference now rounds the cross-entropy gradient's softmax
quotient to float32 before subtracting the target, as the WebAssembly kernels,
both shaders and the Python reference already did; a test pins cpu-js and the
kernels to the same bits over whole training steps.

Without a host, `zipp py` evaluates version-2 graphs on the runtime's tensor
kernels instead of the pure-Python reference, bit-identical to it: the compiled
784-256-10 Adam step went from 939 s to 2.9 s natively, the two interpreter
matmuls being what is left. Eager `F.gelu` uses the exact erf form by default
(`approximate="tanh"` is unchanged), matching PyTorch within 2e-6.

## Python

The frontend runs at 0.59x of its previous time — tuple unpacking 0.21x, list
comprehensions 0.25x, nbody 0.30x, raise/catch 0.44x, the torch rows 0.53x —
and a second pass over the hot paths took it to 0.89x of that: global reads are
emitted inline (0.67x); attribute reads and plain instance stores take a cached
per-class plan through the object model (property reads 0.67x, method calls
0.81x, list append 0.78x); int literals used in loops load once (arithmetic
0.76x); and the interpreter answers `Map.get`, `set` and `has` for a Map
receiver ahead of its method cache, under the same intrinsic proof as before —
the one change JavaScript programs see as well. The CPython differential corpus
grew from 10 to 99 programs, all matching CPython 3.13 in the default,
no-fast-path and no-JIT modes.

Bound methods compare and hash by (function, receiver); a `sort` key that
mutates its list raises instead of looping forever; generators follow PEP 479
and the rest of the protocol; int, float and str subclasses carry a value and
attributes together; and in torch, an in-place update on a tensor that requires
grad reaches the backward pass, `.sum()` over a comparison counts, and binary
cross-entropy is finite at exactly 0 and 1.

## Publishing

The engines served by the site are labelled builds of a published release, so
they are refreshed AFTER this release exists, in one commit that:

1. sets `zippEngineRelease` in `landing/package.json` to `0.0.19`;
2. refreshes `landing/public/playground-runtime` from the
   `zipp-wasm-0.0.19-web-python` asset (`sync-playground.mjs --refresh-engine`)
   and `landing/public/wasm` from `zipp-wasm-0.0.19-web`, both SHA256SUMS-verified;
3. updates the version, size and SHA-256 that `landing/src/App.tsx` and
   `landing/README.md` state about the bundled engine.

Both gates — the landing job's `sync-playground.mjs --require-release` and the
adventure test — compare the served engines against that pin, so they fail if
this step is skipped or half-done, and do not deadlock the release that has to
produce the assets first.
