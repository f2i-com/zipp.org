# ZIPP 0.0.32

A release of fixes and speed for WebAssembly and for programs that embed
ZIPP's WebAssembly modules. WebAssembly in a large program runs on Wasmtime,
a JavaScript object handed to WebAssembly is let go once WebAssembly
can no longer reach it, and the WebAssembly modules hand a host its app's
state as one JSON text instead of thousands of calls across the boundary.
`Reflect.set` and `Object.defineProperty` are faster, and an arrow function
in a class method sees the method's locals over the class's name.

- **WebAssembly in a large program runs on Wasmtime.** 0.0.31 chose a VM's
  WebAssembly runtime by whether its JIT was on, and a JavaScript program of
  256 functions or more starts with its JIT off for its size, as does one
  compiled lazily: every real script fell to the wasmi interpreter. A counting
  loop took 42 ms in a small file and 321 ms once the file also held 300
  unrelated functions. Only the JIT turned off (`ZIPP_NOJIT=1`, an embedder
  disabling it, a trace being recorded) sends WebAssembly to wasmi now.
- **An object handed to WebAssembly is let go.** Wasmtime's runtime kept
  every JavaScript value WebAssembly was ever given as an `externref` for the
  VM's life. A module passing objects by reference, as wasm-bindgen's do, kept
  all of them: an app built that way grew from 3.6 GB to 9.1 GB in two
  minutes in zipp-browser, and now holds steady at about 2.3 GB. A value is
  now released once WebAssembly can no longer reach it, and still comes back
  as itself while it can. (wasmi has no collector for its references, and
  keeps them as before.)
- **A host reads an app's state in one crossing.** The WebAssembly modules'
  `getGlobalsBatch` built what it returned property by property across the
  boundary: for each property a descriptor object, each of its field names
  and the key made on the host's side, and the definition, about eleven calls
  a property. It now writes a batch that JSON can carry exactly as one JSON
  text, charged against the conversion budget exactly as before, and the host
  parses it: each property an own data property, as before, `__proto__`
  included. A batch holding `undefined`, a number JSON cannot spell, a lone
  surrogate or a `Float32Array` converts as it did. Everywhere else a
  property defined on a host object takes two calls instead of eleven. Reading
  the state of a 400-object simulation takes 1.4 ms in Node instead of 8.3,
  and about 2 ms in ZIPP instead of 94.
- **`Reflect.set` and `Object.defineProperty` without a descriptor read
  back.** A descriptor whose fields are data properties of ordinary objects
  is read in place, without naming each field as a new string, and
  `Reflect.set` creates a property as a class field's definition does. Code
  shaped like wasm-bindgen's glue (each call through its `handleError`
  wrapper) runs in 820 ms instead of 1,298; creating 320,000 properties with
  `Reflect.set`, 75 ms instead of 267; `Object.defineProperty` with a literal
  descriptor, 47 ms instead of 84.

## Changes in behaviour

- **`WebAssembly`'s members are writable data properties**, as in a browser:
  writable, configurable and not enumerable. Each was an accessor without a
  setter, so `WebAssembly.instantiate = wrapper` did nothing, without an
  error, and a page or library wrapping it went on calling the original.
  The members become data properties when the first of them is read or
  assigned; before that, `Object.getOwnPropertyDescriptor` still describes
  the accessor.

## Fixes

- **An arrow function in a class method saw the class's name** instead of a
  local of the method with the same name: inside
  `class e { m() { let e = {}; return () => e } }` the arrow returned the
  class. Minified code names both alike; softn.com's UI parser found its
  document root to be its own class and no softn app would open.

## Dependencies

No dependency changed.

## Performance

Measured while 0.0.32 was prepared, on Windows x86-64 (Ryzen 9 9950X3D),
with release builds of the engine without link-time optimization; the
comparison of the published binaries with 0.0.31 follows once measured.

- The `Reflect.set` and `Object.defineProperty` figures above are medians of
  three runs of one program, 160,000 descriptors or 320,000 properties a run,
  under the JIT (the program is small).
- The state read above is `getGlobalsBatch` over 400 objects of ten
  properties, 300 of three and one of three, the mean of 200 reads after 20
  to warm up, in Node 24.19.0 and in the ZIPP command line running the
  Node-target module.
- In zipp-browser, softn.com's predator-prey app read its state 6.9 times a
  second instead of 5.7 with the engine changes alone, on the module softn.com
  serves; the module change reaches an app when it ships a 0.0.32 module.

The figures in the README and
[docs/PERFORMANCE.md](https://github.com/f2i-com/zipp.org/blob/main/docs/PERFORMANCE.md)
still describe the profile-guided 0.0.31 capture of 29 October 2026.

## Publishing

As for earlier releases, the engines the site serves are refreshed AFTER this
release exists, in one commit that:

1. sets `zippEngineRelease` in `landing/package.json` to `0.0.32`;
2. refreshes `landing/public/playground-runtime` and `landing/public/wasm` from
   `zipp-0.0.32-javascript-python.wasm` and `zipp-0.0.32-javascript.wasm`
   (`node crates/zipp-wasm/embed-kit/package.mjs extract`, then
   `sync-playground.mjs --refresh-engine`), SHA256SUMS-verified;
3. syncs the sandbox playground (`node landing/scripts/sync-sandbox.mjs` with
   the release's files) and rewrites the site's Brotli copies
   (`npm run compress:engines`);
4. updates the version, size and SHA-256 that `landing/src/App.tsx` and
   `landing/README.md` state about the bundled engine.
