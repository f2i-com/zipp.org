# ZIPP 0.0.20

Quantized weights on the GPU path, a product computed in integers, and a Python
frontend that runs published model code unmodified -- enough to run Qwen3-0.6B
from its GGUF file, in the browser or split across several machines.

## Downloads

- `zipp-wasm-0.0.20-web.zip`: JavaScript-only browser engine, TypeScript bindings and Worker host SDK.
- `zipp-wasm-0.0.20-web-python.zip`: JavaScript + Python, with the browser GPU adapter, CPU WASM kernels and Torch compatibility guide.
- Native x86-64 CLI archives for Windows and Linux: JavaScript + experimental Python. A source build with `--no-default-features` produces a JavaScript-only CLI.

Every WASM archive includes `BUILD-INFO.txt`, `PROFILE.json` and `SHA256SUMS`.
Publishing requires CI and the full security workflow at the exact tagged commit.

The local-model plugins (`crates/zipp-wasm/model-plugins/`) are an experimental,
source-only package: they run in CI from the tree and are used from a checkout,
and are not in these archives.

## Quantized weights

Graph version 2 takes `dtype: 'q4_k'` and `'q6_k'` on an `input` node, whose
data is the checkpoint's own blocks, and a `transposed` matmul decodes them as
it multiplies -- on the JavaScript reference, the WebAssembly kernels, WebGL2
and WebGPU. A weight stays the size the file has it: Qwen3-0.6B Q4_K_M holds at
373 MB where float32 would need 2,274 MB. The block decoders round as ggml
rounds and are checked bit for bit, for all fifteen formats, against gguf-py,
the llama.cpp project's own implementation. On the reference and the
WebAssembly kernels a quantized matmul equals the same matmul over decoded
values bit for bit; the WebGL2 and WebGPU shaders implement it and generate
sensible text in the browser, but have no recorded bit-for-bit comparison.

A prepared session keeps its weights resident between runs, and caches marked
`carry` stay on the device, so cached decoding uploads one token's inputs a
step rather than the model.

## `matmul_fixed`

A matrix product accumulated in integers: both sides are quantized to int16
against their own row's maximum and the products summed exactly, so the answer
is the same bits on every backend by construction rather than by agreeing on
rounding order -- which is what a proof system over a prime field needs, and
what lets two peers be compared for equality. It costs 1.8e-4 median relative
error against `matmul`. The weight can be quantized once at bind time
(`quantizeWeight`, an `i16` input and its scales), which gives identical bits
and, at one token, runs faster than the float32 matmul it replaces (0.21 ms
against 0.30) for 3.56 times the resident bytes of Q4_K. The JavaScript
reference and the WebAssembly kernels implement it; WebGPU and WebGL2, which
have no 64-bit integer to accumulate in, refuse the graph rather than return
zeros. `gpu-lab/docs/FIXED-POINT.md` has the measurements.

## WebAssembly kernels

The CPU kernels are now `no_std` Rust (`crates/zipp-wasm/rust/zipp-kernels`)
rather than C, with SIMD panels and the block decoders shared with the GGUF
reader. The committed `kernels.wasm` builds to the same bytes on Linux and
Windows -- recorded paths are remapped and symbol names stripped -- and CI now
rebuilds it and fails if the result differs from what is committed.

## Python

- Relative imports resolve as CPython resolves them, so a package can be copied
  in rather than rewritten; climbing past the top package is an error.
- `torch.autocast` is a context manager that does nothing, which is exact here:
  every tensor is float32 already.
- The torch subset gains `sin`, `cos`, `rsqrt` and `repeat_interleave`.

With those, Hugging Face's `modeling_qwen3.py`, `modeling_qwen2.py`,
`modeling_llama.py` and `modeling_mistral.py` compile and run exactly as
published, within 1.8e-7 of what transformers computes for the same weights.

## Local models (source only)

`model-plugins/` holds the host side: a plugin registry that installs a model
architecture as hashed Python source, Safetensors and GGUF readers that never
hold the file (a 6.8 GB checkpoint opens in 35 ms), cached decoding, and a
Qwen3 plugin. Against a GGUF of Qwen3-0.6B it answers "The capital of France
is" with " Paris", its logits within 7.4e-5 of transformers reading the same
file over 455,808 of them, at about four tokens a second on the WebAssembly
kernels. A model divides into stages -- any ranges of layers -- that together
reproduce the whole model's logits bit for bit, across worker threads too; each
stage says which configuration and which weights it ran, and refuses a hidden
state from any other. A prompt runs a chunk of positions at a time into the
same caches, bit for bit with one position a step and 2.8 times faster.

## Engine

The JavaScript engine is unchanged from 0.0.19: no source it compiles by
default has changed, so the native workspace suite and Test262 test the same
code they passed for that release.

## Publishing

As for 0.0.19, the engines the site serves are refreshed AFTER this release
exists, in one commit that:

1. sets `zippEngineRelease` in `landing/package.json` to `0.0.20`;
2. refreshes `landing/public/playground-runtime` from the
   `zipp-wasm-0.0.20-web-python` asset (`sync-playground.mjs --refresh-engine`)
   and `landing/public/wasm` from `zipp-wasm-0.0.20-web`, both SHA256SUMS-verified;
3. updates the version, size and SHA-256 that `landing/src/App.tsx` and
   `landing/README.md` state about the bundled engine.
