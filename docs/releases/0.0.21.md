# ZIPP 0.0.21

A Python frontend that runs within about 1.75x of CPython 3.13 on the command
line, a torch layer broad enough for ordinary training code, torch as an
optional WebAssembly package, and `torch.compile` graphs on a hardware GPU
natively -- a small model's training step faster than PyTorch's eager CUDA on
the same card.

## Downloads

- `zipp-0.0.21-x86_64-pc-windows-msvc.zip`: native CLI for Windows, complete: JavaScript, Python, torch and native GPU.
- `zipp-0.0.21-x86_64-unknown-linux-gnu.tar.gz`: the same native CLI for Linux.
- `zipp-wasm-0.0.21-web.zip`: JavaScript-only browser engine, TypeScript bindings and Worker host SDK.
- `zipp-wasm-0.0.21-web-python-base.zip`: JavaScript + Python without torch; add torch from `web-torch` when a page needs it.
- `zipp-wasm-0.0.21-web-python.zip`: JavaScript + Python complete, torch built in, with the browser GPU adapter and CPU WASM kernels (the same role as 0.0.20's).
- `zipp-wasm-0.0.21-web-torch.zip`: the torch package, `zipp_torch.wasm` and its `zipp_torch.js` loader, added to `web-python-base` through `addPythonPackage`.
- `SHA256SUMS` for every asset.

Every WASM archive includes `BUILD-INFO.txt`, `PROFILE.json` and `SHA256SUMS`.
Publishing requires CI and the full security workflow at the exact tagged commit.

The local-model plugins (`crates/zipp-wasm/model-plugins/`) remain an
experimental, source-only package: they run in CI from the tree and are used
from a checkout, and are not in these archives.

## Python performance

Over the 36 programs of the Python benchmark suite the command line now runs at
about 1.75x CPython 3.13's time with the JIT, from about 22x when this round
began, and `range_loop`, `int_arith`, `float_arith`, `tuple_swap` and
`global_read` beat CPython. The gains come from direct calls (`PyCall`),
per-VM inline caches and fused Python instructions, small integers stored in
the value word, dicts and sets in a native compact table, hidden-class
instance layouts, and a Python JIT tier that compiles hot loops. The JIT tier is
x86-64 and command-line only; WebAssembly, the sandbox and budgeted embedders
stay interpreted, with every result the interpreter's.

## Python compatibility and torch

Uncaught exceptions print CPython's traceback, traceback objects and the
`traceback` module give CPython's frames, and complex numbers and `cmath` follow
CPython 3.13 byte for byte. The torch layer gains about 200 tensor functions,
the layers, losses, optimizers and schedulers common training code uses,
`torch.utils.data`, `torch.linalg` and `torch.fft` (both native), complete
`torch.distributions`, float16/bfloat16 in two bytes with CPU autocast, complex
and sparse tensors, quantization and single-process `torch.distributed`, each
checked against values PyTorch 2.11 generated. Eager torch's heavy loops run as
native kernels with byte-identical JavaScript fallbacks, and Hugging Face's
GPT-Neo modelling file now runs unmodified too. The scope and what is still
missing are in the
[Torch compatibility guide](https://github.com/f2i-com/zipp.org/blob/v0.0.21/docs/TORCH_COMPATIBILITY.md).

## Torch as a package, and the WebAssembly sizes

Torch is now optional in the browser: the `python` engine leaves it out, and
`zipp_torch.wasm` adds it at run time after the engine checks its format, engine
ABI hash and the SHA-256 of every file; without it, `import torch` raises
`ModuleNotFoundError` saying how to add it. The complete engine keeps torch
built in and is unchanged for existing hosts. Sizes (Brotli-11):
JavaScript about 1.33 MB, Python without torch about 1.70 MB, complete about
2.06 MB, and the torch package about 0.38 MB. Before it ships, the release
workflow runs the torch suites on the Python engine plus the package and on the
complete engine, and requires the same output byte for byte.

## Native GPU

`zipp py` runs `torch.compile` and `zipp_gpu` graphs on a hardware GPU through
wgpu (Vulkan, Direct3D 12 or Metal), executing gpu-lab's WGSL kernels
synchronously so a program's output does not depend on whether a GPU is
present, and falling back to the CPU evaluator when there is none. Prepared
steps replay natively, kernels fuse only where every element's arithmetic is
unchanged, and large matmuls use a 128x128 tile (48 TFLOP/s on a 4096³
product). On an RTX 5090 a small MLP's prepared step takes 0.27 ms (0.12 ms at
eight steps per run) against about 0.78 ms for PyTorch's eager CUDA (0.17 ms for
its CUDA graph); large matmuls are still slower than CUDA's. The graph protocol
is now version 4 (masks, dropout, slicing, gathers and index gradients),
labelled only when a graph uses it, so an older host refuses rather than
misreads it.

## Parser, startup and determinism

Python is parsed by ZIPP's own front end, `crates/zipp-pyparse`, and compiled
from its syntax tree directly; the RustPython parser fork is removed, the
compiled output is byte-identical over 61,885 programs, and the Python module is
smaller. The CLI caches compiled code per user, so a Python hello-world starts in
about 20 ms, and the WebAssembly engine's `prewarmPython()` brings the first
browser run from about 220 ms to about 20. The compiler now emits the same
bytecode on every run.

## Engine

Small BigInts are immediates in the value word, which makes JavaScript BigInt
code 2-4x faster, and a JIT wrap that changed results, a missed temporal dead
zone in destructuring and nested budget loans are fixed, with the other
JavaScript benchmarks unchanged and Test262 passing as before. The WebAssembly
host boundary and the playground's dev server received a round of fixes.

## Publishing

As for 0.0.20, the engines the site serves are refreshed AFTER this release
exists, in one commit that:

1. sets `zippEngineRelease` in `landing/package.json` to `0.0.21`;
2. refreshes `landing/public/playground-runtime` from the
   `zipp-wasm-0.0.21-web-python` asset (`sync-playground.mjs --refresh-engine`)
   and `landing/public/wasm` from `zipp-wasm-0.0.21-web`, both SHA256SUMS-verified;
3. updates the version, size and SHA-256 that `landing/src/App.tsx` and
   `landing/README.md` state about the bundled engine.
