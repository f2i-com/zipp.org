# ZIPP 0.0.34

An interpreter release, with two fixes for compiled code. On the x86-64
command lines, interpreted loops and the calls they make now run through a
second, leaner form of the interpreter. That speeds up a program run with
the JIT off, and the loops of a large program, which is interpreted either
way. Over 90 benchmark programs 0.0.34 interpreted takes 0.90x 0.0.33's
time and is ahead of `node --jitless` on 65 of the 89 that Node runs,
where 0.0.33 is ahead on 52; with the JIT it is level with 0.0.33 and
ahead of Node 24 on 70 of the 89. The bundled applications, whose time is
in calls between many functions rather than in loops, are level. One bug
that 0.0.31 to 0.0.33 shipped is fixed: a global that was deleted, or
given a getter, a setter or read-only attributes, by something a running
compiled loop or function itself called went on being read and written as
the plain variable it had been until that code returned. And the
experimental optimizing tier (`ZIPP_OPT=1`, off by default) no longer runs
forever on a function whose body starts with a loop.

## New in 0.0.34

- **Interpreted loops run through handlers that jump from one to the
  next.** The interpreter's dispatch loops are each one large function,
  and an instruction there costs about fifty machine instructions. At a
  loop that has run a while the interpreter now hands the frame to a
  runner in which every instruction is a small function of its own, its
  operands decoded once, that does the work for the operand kinds a loop
  usually has and jumps straight to the next. Arithmetic and bitwise
  loops, typed-array and array loops, property reads and writes,
  `charCodeAt` scans, switches and `DataView` loops take between a half and
  three quarters of the time they took. The runner is in the x86-64 builds for now; the Arm
  builds and the WebAssembly engines run loops as before.
- **Calls stay in it.** A small function whose body only computes is run
  without a frame; any other plain function or method gets its frame
  pushed and popped by the runner itself, so a loop that calls functions
  which call functions keeps its speed. Interpreted, `call0` takes 0.84x 0.0.33's time,
  `class_method` 0.86x, `calls-baseline` 0.88x, `call_method` and
  `recursion-shapes` 0.90x.
- **The rest of the language is reachable from it.** String, array, `Map`,
  `Set` and number methods, element reads and writes of every kind, string
  building (`a + b + c`, `s += x`, template literals), getters and
  setters, object and array literals, closures, `try` blocks and every
  kind of `for…of` run from inside the runner, with errors, callbacks that
  re-enter it and garbage collection handled where they arise. Whatever it
  does not do is handed to the ordinary loop for that one instruction, and
  a loop that keeps being handed over is left to the ordinary loop for
  good, so a program the runner does not suit runs as it did.
- **Sites that many object layouts reach.** A property read, write or
  method call in such a loop asks every layout its site has seen, as the
  ordinary loop does, so code over objects of several classes or shapes
  gains with the rest. `polymorphic-objects-v2` takes 0.83x and
  `property-ic-shapes` 0.84x.
- **`DataView` accessors in the interpreter** are found by their place in
  `DataView.prototype` rather than by name, fused or split
  (`dv.getUint32(o, le)` with a global among its arguments). With the runner,
  `dv_get` takes 0.62x and `dv_get_glob` 0.59x.
- **Inherited properties and accessors, and `super` accessors,** answer on
  one compare of a chain epoch instead of a walk that re-proves every hop.
  `proto_read` takes 0.66x interpreted and `class-prototype-hot` 0.80x.
- **Compiled code.** A method whose body makes an instance is inlined with
  the instance made in place; a typed lane multiplies an integer by a
  positive constant as integers.

## Changes in behaviour

- `ZIPP_NO_LOOP_RUNNER=1` keeps every loop in the ordinary interpreter
  loop, and `ZIPP_NO_LOOP_FRAMES=1` keeps the runner from pushing frames;
  both are for comparison. Nothing else changes.

## Fixes

- **A global changed under running compiled code kept its old meaning.**
  Compiled code reads and writes a global through its slot, and checked
  that the slot was still the variable only when the code was entered. If
  something that code called (a callback, a function, a getter) deleted
  the global, or put a getter, a setter or read-only attributes behind it
  with `Object.defineProperty(globalThis, …)`, the running loop or function
  went on using the slot until it returned: reads answered the old value,
  a read of a deleted global returned instead of throwing a
  `ReferenceError`, writes skipped the setter and the read-only check, and
  a call through a replaced global function went to the old one. The
  interpreter was always right, and so was the next call of the compiled
  function; only the activation already running was wrong. Compiled code
  now notices the change at its next access of any global and hands that
  instruction to the interpreter.
- **The experimental optimizing tier never left a loop at a function's
  first instruction.** With `ZIPP_OPT=1` (off by default), a function whose
  body starts with a loop over its parameters, such as
  `function f(n) { while (n > 0) n--; return n; }`, was compiled with the
  values the loop carries read as the parameters again on every
  iteration: a release build never finished the call, and a debug build
  failed an assertion. 0.0.33 has it too. The tier now leaves such a
  function to the baseline compiler. Reported with its reduction by
  codeandsolder (#93).

## Performance

Measured on 11 November 2026 on an otherwise idle machine, native Windows
x86-64 (Ryzen 9 9950X3D): the published 0.0.33 Windows binary against the
0.0.34 Windows binary from the release build's dry run, built from this
release's engine source by the same profile-guided recipe, with Node
24.19.0 in the same runs. Both ZIPP binaries run with address-space
randomization turned off and the code cache off, pinned to one core; the
figures are medians of 5 interleaved runs (7 for the three programs timed
separately). Every one of the 90 programs prints the same output under
0.0.33 and 0.0.34 in both lanes. The 0.0.34 binary measured is the one
built before the optimizing tier's fix above, which changes nothing unless
`ZIPP_OPT=1` is set.

**The 90 benchmark programs** (the 78 of earlier releases, the seven
bundled applications and five TypeScript benchmarks compiled to
JavaScript). The geometric means are over the 87 programs one pass timed
with all three engines; the other three (the TypeScript bundle, which Node
cannot run, and two ES-module programs) were timed separately and are
given below, and the counts against Node include the two modules.

- **Interpreted** (`ZIPP_NOJIT=1 ZIPP_NO_RX_JIT=1`, no native code at all):
  0.896x 0.0.33's time, faster on 68 of 87 and by more than 2% on 55. The
  largest gains are `f64_write` (0.49x), `arr_write` (0.54x), `arr_read`
  (0.58x), `dv_get_glob` (0.59x), `dv_get` (0.62x), `proto_read` (0.66x),
  `typedarray-math` (0.67x), `g_f64` and `f64_read` (0.69x), `i32_rw`
  (0.70x), `g_counter` and `prop_write` (0.71x), `glob_loop` (0.73x),
  `bytecode-vm` (0.74x), `prop_read` (0.76x), `class-prototype-hot`
  (0.80x), `branch-control` (0.82x), `parse-large-js` and
  `polymorphic-objects-v2` (0.83x), `call0` and `property-ic-shapes`
  (0.84x). Slower by more than 2%: `warm-router` (1.22x), `collections`
  (1.07x), `numbers-format-parse` and `map-set-heavy` (1.05x),
  `class-features` and `large-heap-churn` (1.03x), `babel` and
  `destructuring-spread` (1.02x). `warm-router` is the runner's doing: a

- **Against `node --jitless`, interpreted:** 0.863x its time, ahead on 65
  of the 89 programs Node runs, where 0.0.33 in the same runs takes 0.964x
  and is ahead on 52. Thirteen programs changed sides and none went back:

## Publishing

As for earlier releases, the engines the site serves are refreshed AFTER this
release exists, in one commit that:

1. sets `zippEngineRelease` in `landing/package.json` to `0.0.34`;
2. refreshes `landing/public/playground-runtime` and `landing/public/wasm` from
   `zipp-0.0.34-javascript-python.wasm` and `zipp-0.0.34-javascript.wasm`
   (`node crates/zipp-wasm/embed-kit/package.mjs extract`, then
   `sync-playground.mjs --refresh-engine`), SHA256SUMS-verified;
3. syncs the sandbox playground (`node landing/scripts/sync-sandbox.mjs` with
   the release's files) and rewrites the site's Brotli copies
   (`npm run compress:engines`);
4. updates the version, size and SHA-256 that `landing/src/App.tsx` and
   `landing/README.md` state about the bundled engine.
