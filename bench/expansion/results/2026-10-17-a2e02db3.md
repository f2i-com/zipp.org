# Zipp's interpreter against Bellard's QuickJS: coverage expansion, 2026-10-17

**Diagnostic series, not a canonical result.** The canonical real13 and
micro5 suites, and their published geomeans, are unchanged. This records
where Bellard's QuickJS still beats Zipp's interpreter on a broader set of
workloads, the evidence, and what to do about it.

## Setup

| | |
|---|---|
| Zipp | `a2e02db3` (clean tree), PGO build of the repository's ad-hoc recipe, interpreter only (`ZIPP_NOJIT=1`); binary sha256 `c9c473a1878f7a26…`, 16,919,040 bytes |
| QuickJS | Bellard's QuickJS 2026-06-04 `qjs.exe`, sha256 `2af36cc5c6fc9650…` |
| Output reference | Node v24.19.0: every engine's stdout equals Node's, byte for byte, for every case and size (nothing was excluded) |
| Machine | AMD Ryzen 9 9950X3D (16 cores, 32 threads), Windows 11 26200; otherwise idle |
| Method | `bench/comparison/run_native.py`: 15 counterbalanced repetitions (engine order rotated and reversed per cycle, case order shuffled per repetition); each full run preceded by an empty launch of the same engine |
| Metric | startup-adjusted process CPU cycles (full run less the empty launch); 95% percentile-bootstrap interval of the median ratio, repetitions resampled within each case. A row whose interval contains 1 would be reported AMBIGUOUS; none did |

Ratios are Zipp ÷ QuickJS: below 1, Zipp is faster.

## Summary

| Suite | Rows | Geomean | Category-balanced | Zipp faster | QuickJS faster |
|---|---|---|---|---|---|
| Interpreter 18 (real13 + micro5, 5 interleaved runs, wall time) | 18 | **0.580** | — | 16 | 2 (fib 1.21, property-ic-shapes 1.21) |
| Hostile 17 | 17 | **0.760** | 0.786 | 12 | 5 |
| Expansion 21 at s, m, l | 63 | **1.172** | 1.223 | 26 | 37 |

The canonical rows and the hostile suite favour Zipp (1.7x and 1.3x
overall). The expansion suite, built to find blind spots, does not: QuickJS
is ahead overall, and by 1.6-3x in five areas (Proxy and accessors, class
private members, dictionary deletes, generated code, Unicode strings).
Startup is not the cause anywhere: Zipp's empty launch costs about 0.78x
QuickJS's on every row. Small inputs lean towards QuickJS more than medium
and large ones (per-script setup and compilation), and Zipp's peak working
set is 3-8x QuickJS's on most allocating rows (64x on `eval-function@l`, a
leak).

A measurement note: the first hostile capture, started a minute after the
pinned binary was written, recorded bytecode-vm at 1.087 while every other
row matched a rerun within 2%; nothing in the launch conditions reproduces
it (working directory, pipes, environment filtering, an empty launch before,
either CCD), and a full rerun gave 0.911. The rerun is the reported result;
leave a freshly built binary a few minutes (antivirus scanning is the likely
cause) before a capture.

## Prioritized weaknesses (where QuickJS still wins)

Ranked by practical impact (how common the operation is in real programs),
repeatability (seen in the 15-rep capture, or only in single runs), and how
well the mechanism is understood. Effort: S (a day), M (a few days), L (a
data-structure change).

| # | Weakness | Evidence | Suspected subsystem / mechanism | Effort |
|---|---|---|---|---|
| 1 | Recursive calls (m5_fib 1.2x) | 18-row suite; PC profile | frame push/pop: 88-byte `Frame` (24-byte handlers Vec), window fill, bounds-checked argument copy, callee `FuncProto` loads (~44% of fib) | M |
| 2 | Proxy traps and accessors (accessors-proxy 3.0x at every size; a set trap forwarding through Reflect.set 18x in isolation) | expansion capture; isolated probe | trap call path: per-call argument arrays, receiver/invariant checks around each trap | M |
| 3 | Deleting from large dictionaries (dict-churn 2.7x at every size) | expansion capture; probe scaling with key count | `ObjMap::remove_at` shifts keys/vals/attrs and re-slots the hash index: O(keys) per delete | L (tombstones) |
| 4 | Class private members, `#x in`, derived constructors (class-features 2.5-3.0x) | expansion capture; per-op probes | private-name side table lookups and brand checks out of line; derived-constructor frame setup | M |
| 5 | Memory: peak working set 3-8x QuickJS | every allocation-heavy row | tracing GC heap-growth policy vs QuickJS refcounting; `new Function` code never reclaimed (~1.4 KB each) | M (policy), S (leak) |
| 6 | Unicode strings (strings-unicode-scan 1.8-2.0x; within it two-byte `indexOf` 3.8x, case mapping 2.3x, `for-of` 1.75x; random `charCodeAt` into non-ASCII text costs the distance); string building 1.2-1.8x | expansion capture; per-section timings | WTF-8 storage: unit index lookups walk from a single remembered position | M-L |
| 7 | Generators, `yield*` (generators-iterators 1.7x, 2.2x small; 2.2x on delegation alone) | expansion capture; section timings | generator resume/suspend frame save and restore | M |
| 8 | Compiling generated code (eval-function 1.7x, 2.9x small; regex compile 2.4x in isolation) | expansion capture | parse+compile pipeline per call; regex compile | M |
| 9 | Module top-level loops (module-hot-graph 1.45x after the FxHash fix), type churn (1.27x), closures from interpreted loops (1.19x), throw/catch (1.12x), branchy code (1.06x) | hostile17 capture | main-loop register pressure (the lite loop now skips short entries); exception unwind path | M |
| 10 | An LRU cache under churn (large-heap-churn 1.7-2.0x) | expansion capture | Map with string keys and linked-list updates under GC pressure; the collector at large heaps | M |

Already fixed during the investigation (each its own measured commit):
module namespace lookups (SipHash -> FxHash: module-hot-graph -22%),
`Array.prototype.slice` scanning the whole array for holes (61 -> 1 ms),
string search copying a receiver with a lone surrogate (148 -> 0 ms),
the register file's hidden bounds check (every interpreter row 3-15%),
closures and short entries in the lite loop.

## Optimization plan (small, measurable experiments)

Each step: a minimal reproducer, a profile, one focused change, a same-binary
A/B, then a clean PGO build compared on the 18-row suite, hostile17,
expansion, JIT real13/hostile and Python micro. Negative results are kept.

1. **`new Function` leak** (S): find what keeps a dropped dynamic function's
   `FuncProto` alive; reclaim it. Measure peak working set on the reproducer.
2. **Frame push** (M): a lite-loop push with per-callee facts cached at
   decision time; `Frame` to 64 bytes (`handlers` as an 8-byte pointer).
   Target: fib under 1.0x QuickJS.
3. **Proxy traps** (M): profile the set/get trap path; remove per-call
   allocations; cache trap lookups per handler shape.
4. **Private members** (M): resolve private names to slots at compile time
   where the class is static; inline the brand check.
5. **Dictionary deletes** (L): tombstones in `ObjMap` with compaction on
   growth or iteration; property caches already reject dictionary-mode
   objects.
6. **GC heap growth** (M): measure pause/footprint trade-offs of a smaller
   young generation or growth factor on the gc rows; report memory and
   time together.
7. **Unicode strings** (M-L): a sampled unit-index table for long non-ASCII
   strings (bounded memory) for random access, and a two-byte search path.
8. **Generators** (M), **regex/`new Function` compile** (M), **number
   formatting, BigInt, DataView** (S each).

Canonical scoring is unchanged throughout; any change to it waits for a
complete clean capture to be reviewed.

## WebAssembly (separate track, not run)

Not measured in this pass. A comparison needs an actual QuickJS WebAssembly
build: this machine has neither a WASI toolchain nor QuickJS's source, and
QuickJS ships no official WebAssembly binary. The plan: build QuickJS
2026-06-04 for `wasm32-wasi` with a pinned wasi-sdk, run it under Node's
`node:wasi` beside Zipp's shipped `javascript` module through
`bench/comparison/run_wasm_suites.mjs`, and report transfer size, start-up
and steady state separately, with the host-interface and limit differences
documented. A native-interpreter result is not evidence for WebAssembly.
